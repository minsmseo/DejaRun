## 1. One app reading Jira and Confluence

**Confirmed**

- Declare products under `app.compatibility`. Exactly one product is required, others are optional. For DejaRun:

  ```yaml
  app:
    compatibility:
      jira:
        required: true
      confluence:
        required: false
  ```

  The docs show only the Confluence-required example; the Jira-required form above is the same structure the GateReady app in this account deployed with.
- Install order: required product first, then `forge install -p confluence`. This is per Forge environment. After scope changes: `forge deploy`, then `forge install --upgrade`.
- Frontend calls: `requestJira` and `requestConfluence` from `@forge/bridge`. Backend calls: `api.asUser().requestConfluence(route...)` or `api.asApp().requestConfluence(route...)` from `@forge/api`. `asUser()` is only available in modules that support UI Kit, so a trigger must use `asApp()`.
- Uninstalling from the required product uninstalls the optional ones.
- "Currently multiple-app compatible Forge apps are restricted to a single site."
- Multiple-app apps "can only be listed on Marketplace as paid apps; free listings are not supported."

**Unconfirmed**

- Lifecycle label of required/optional compatibility. The page calls a newer "Global Apps" model EAP; that model is not what we use.
- What `requestConfluence` returns from a Jira module when Confluence is not connected.

**Design impact**

- Jira is the required product. Confluence is optional, so backfill and report links must degrade to a clear "Confluence is not connected" state.
- The Marketplace bonus would require a paid listing. See the open decisions at the end.

## 2. Issue created and updated events

**Confirmed**

- Event names: `avi:jira:created:issue`, `avi:jira:updated:issue`, `avi:jira:deleted:issue`. Scope: `read:jira-work`.
- `trigger` module properties: `key`, `function`, `events`, optional `filter` (`ignoreSelf`, `expression`, `onError`, `appIsLicensed`).
- The app's own writes fire the event again. The payload has `selfGenerated`; `filter.ignoreSelf: true` drops those events.
- Updated-event payload: `issue`, `changelog` (each entry has `from` / `to`, and `fromString` / `toString` for a fixed list of system fields), `associatedUsers`, optional `customFields`.
- Events "may take up to 3 minutes" to arrive. Events over 200 kB are not delivered.
- Retries: at most four, by returning `InvocationError`.

**Unconfirmed**

- Whether a change to an issue entity property fires `avi:jira:updated:issue`.
- Trigger function timeout and delivery guarantee.

**Design impact**

- The trigger is for the Duplicate comment and for keeping the stored verdict current. It cannot be the only path: conditions are saved from our own panel into Forge storage, which is not a Jira field change, and delivery can lag. Saving conditions in the panel must run the check directly in the resolver. The trigger covers issue creation and field edits.
- Use `ignoreSelf: true`, because the app adds comments and issue links.

## 5. Forge storage

**Confirmed**

- Current package is `@forge/kvs` (`import { kvs } from '@forge/kvs'`). The `storage` export of `@forge/api` is legacy with a migration guide. Scope: `storage:app`.
- Custom Entities are declared under `app.storage.entities` with `attributes` (types `string`, `integer`, `float`, `boolean`, `any`) and `indexes` (simple, or named with `partition` and one `range` attribute).
- Query: `kvs.entity('name').query().index('index-name', { partition: [...] }).where(WhereConditions.equalTo(...)).limit(n).cursor(c).getMany()`. `limit` default 10, maximum 100. Queries are eventually consistent; `get` by key is strongly consistent.
- Limits: value 240 KiB, 20 entities per app, 50 attributes per entity, 7 indexes per entity.
- After a deploy that changes entities, indexing takes at least 5 minutes and the app cannot be installed until it finishes (`forge storage entities indexes list -e <environment>`). Entities and attributes cannot be deleted after deployment.
- Runs on Atlassian requires Atlassian-hosted compute and storage and no egress. `forge eligibility` checks it.

**Unconfirmed**

- The manifest index page labels app storage "(EAP)" in one place while the storage pages treat Custom Entities as standard.
- The docs spell one condition both `equalTo` and `equalsTo`. Check the installed package typings.

**Design impact**

- Experiment records fit Custom Entities: one `experiment` entity with a partition index on project plus `system`, so a check loads only candidates for the same project and system, then the similarity engine runs in memory. Parameters are schema-defined per project, so they go into one `any` attribute and are never indexed.
- Parameter schemas and project settings are single documents per project: plain `kvs.set` / `kvs.get`.
- Because entities and attributes cannot be deleted, settle the entity design in step 6 before the first deploy that includes it.

## 7. Teamwork Graph API

**Confirmed**

- Status: Preview since 15 October 2026 (changelog). The current call guide and limitations page no longer mention allowlisting.
- Call from the frontend with `requestTeamworkGraph(query, variables?)` from `@forge/bridge`, returning `{ data?, errors? }`. Call from the backend with `api.asUser().requestTeamworkGraph(...)` from `@forge/api`.
- "Calls always run as the current user; Forge apps can't call the Teamwork Graph API as the app."
- Scopes are per object type: `read:graph:issue:jira`, `read:graph:project:jira`, `read:graph:page:confluence`, `read:graph:space:confluence`, `read:graph:user:atlassian`, `read:graph:team:atlassian`. The broad `read:graph:jira` and `read:graph:confluence` are being retired.
- New apps use curated queries or persisted Cypher queries. Raw Cypher is unavailable to new apps.
- Curated fields that exist: `atlassianUserInTeams(userId: ID!)`, `atlassianTeamMembers(teamAri: ID!)`, `atlassianUserAssignedJiraWorkItems(userId: ID!)`, `atlassianTeamsBySpace(spaceAri)`, `confluencePageLinkedConfluencePages(id)`, `confluencePageContributors(id)`. User ids are ARIs: `ari:cloud:identity::user/<accountId>`.
- Curated fields that do not exist: work item to assignee, work item to linked work items, work item to Confluence pages.
- Pagination: `first` / `after`, `pageInfo { hasNextPage endCursor }`, `first` capped at 25. A page can be short and still have a next page.
- "A missing or disabled scope does not produce an error." Data the scope would have allowed is simply absent. Persisted-query errors arrive with HTTP 200 in `errors[].extensions.code`.
- Installing an app with Teamwork Graph scopes requires organization administrator permissions.
- Persisted Cypher queries are registered by `POST https://<site>.atlassian.net/gateway/api/twg/cypher-queries` and run with `customQuery(queryKey:, queryParams:, first:)`. No manifest key or CLI command for registration is documented.

### Proposed redesign of step 13 (people instead of teams)

The table above reflects the design in CLAUDE.md, which depends on team lookups that fail. The design below uses only queries that returned real data in the fourth run. It keeps the purpose, attaching "who did this" to a duplicate warning, and replaces teams with people. The owner approved it on 2026-11-17 and CLAUDE.md section 6 now describes it.

| Feature | What it shows | Graph query | Status |
|---|---|---|---|
| **Who ran it** ("Ask the people who ran it") | For a past experiment: the Jira assignee, plus the creator and contributors of its Confluence report. For experiments that exist only as a report (backfilled, no assignee) the graph is the only source of a person to ask. | `confluencePageCreator`, `confluencePageContributors` | Verified |
| **What they are running now** | Under each person, their open work items, so the researcher can see whether that person is still on the topic. | `atlassianUserAssignedJiraWorkItems`, filtered in code to `statusCategory.key != done`, capped at one page of 25 | Verified |
| **Connected context** | Pages linked from the report page, added to the evidence list. Work item to work item links come from the Jira REST API, since the graph has no curated query for them. | `confluencePageLinkedConfluencePages` | Query accepted; non-empty result not yet seen |
| **Others on this system** (was "Other teams on this system") | Planned or running experiments on the same system from our own records, with their owners. No team names. | None needed; owner names from Jira | Reduced: no graph part |

Agent actions change accordingly: `get-run-owners` returns the assignee and the report's creator and contributors (no teams); `find-teams-on-system` becomes `find-people-on-system` and reads only our records and Jira.

Costs and limits of this design:

- Scopes: `read:graph:user:atlassian`, `read:graph:issue:jira`, `read:graph:page:confluence`. `read:graph:team:atlassian` is dropped. Installing still needs an organization admin.
- Each person shown costs one graph call for their work items, so the panel caps the number of people (for example the top three matches).
- Fallback is unchanged: if a call fails, hide that area and show the Jira assignee and reporter.

- All Teamwork Graph calls must happen in a user context (panel, page, agent action). The issue-event trigger cannot call it, so team information is fetched when a person looks, never stored by the trigger.
- Judges' install instructions must say that an organization admin has to install the app if these scopes stay in the manifest.

## Findings from building steps 4 to 13 (2026-11-17)

All observed on the development site with app versions 6.0.0 to 9.0.0.

| Area | Observed |
|---|---|
| Storage | Plain KVS with key prefixes (`@forge/kvs`, `kvs.query().where('key', WhereConditions.beginsWith(prefix))`) is used instead of Custom Entities. A project has tens to hundreds of records, all of which are compared in memory, so no index is needed, and KVS has no indexing wait and no undeletable entities. |
| Issue panel | A `jira:issuePanel` is added per work item from the app button under the title. Changing the module `key` removes the panel from work items that had it. |
| Issue panel for all work items | The panel's menu has **Show for all work items**. It applies to the project the work item is in: after choosing it in BAF, a BAF work item that never had the panel showed it, a CCP work item did not. |
| Issue context | `jira:issueContext` appears on every work item without being added. With `dynamicProperties` the lozenge is visible while the entry is collapsed. Function keys are limited to 23 characters. |
| UI Kit text inputs | A `Textfield` or `TextArea` reports its value a moment after the last keystroke. Clicking a button straight after typing submitted the previous value. The panel now waits 300 ms and reads the latest value from a ref before submitting. |
| Manifest | Action and input `description` values are limited to 255 characters, and a plain YAML scalar must not contain `: `; quote such values. |
| Cross-product | Adding Confluence scopes makes the CLI ask for `forge install -p confluence`. With `app.compatibility` (Jira required, Confluence optional) both installs succeeded and Confluence REST v2 calls from Jira modules work as the user. |
